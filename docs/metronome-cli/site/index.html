metro - billing without the Metronome maze

You do not need to know Metronome's UI or billing config to help a customer. Metro is your window into plans, credits, and contract changes: paste a name, see what is true today, preview what would change, then apply only when you mean to - without digging through screens or guessing endpoints.

Try it

Four steps most engineers need

Start with install (no API key). When someone pastes a customer name from Slack, use metro ops who - metro tells you the plan and the next safe command. Deeper API gates exist when you need them; you do not start there.

1. Install and prove the binary

git clone --depth 1 https://github.com/metrocli/metro.git ~/.metro/src 2>/dev/null || true
bash ~/.metro/src/scripts/install-global.sh
metro doctor
metro setup quickstart --shell | zsh
metro schema --json

Installs the standalone package, writes temp fixtures, validates pro-annual, and emits a sandbox preview hash. No Metronome API calls.

2. Set your power ceiling, then look up

metro mode set read-only
metro ops who "Acme Capital" --prod
metro mode set read-write   # only when you need to apply

Mode sticks in ~/.metro/mode.json until you change it. Schema, gates, and confirm tokens stay underneath - mode is just the ceiling so read-only work cannot write.

3. Discover commands when you are stuck

metro docs command-reference --json
metro docs explain first-safe-preview --json
metro docs explain output.anatomy --json
metro api readiness --summary --json

Same catalog that powers this site: modes, live-guarded status, schema versions, and exit code 0 / 1 / 2.

4. Optional guarded sandbox read / write

export METRONOME_SANDBOX_KEY='your-sandbox-key'
metro api read contracts.get.v2 --file request.json --sandbox \
  --read-gate read-gate.json \
  --confirm-live-read I_UNDERSTAND_THIS_WILL_READ_LIVE_METRONOME --json

Only when you already know the endpoint path. Prefer metro ops who and workspace pack commands for sales one-offs. Without a key or gate, metro refuses on stderr with exit 2.

Setup

Install path, configuration, and first preview

The CLI starts local-first: load a JSON or YAML file, validate a shape, render a preview, and stop before any live client can load.

Profile check

metro setup template --json
metro setup doctor --file profiles.json --json
metro setup resolve --file profiles.json --profile my-sandbox --expect-tenant sandbox --key-fingerprint fp_sandbox_reviewed --json

Profile files store tenant and environment variable names only. The local doctor reports whether the named variables are present, and the resolver emits a secret-free tenant binding for future gates without authorizing live API access.

Profile model

CLI profiles must resolve to exactly one tenant. A profile may point to `METRONOME_SANDBOX_KEY` or `METRONOME_PROD_KEY`, but key presence is never authorization to call the API.

architecture safety

First safe preview

The first supported user journey should load local input, validate the selected shape, render a preview, produce a payload hash, and stop before any apply path.

Safety model

Every command must declare its risk boundary

Billing operations need boring, visible gates. The CLI should make tenant, side effects, proof, and rollback state impossible to miss.

No live reads or writes by default. A local `.env`, API key, script name, or dry-run flag is not permission. Production and sandbox share `https://api.metronome.com`; the bearer token selects the tenant.

Validator rules

Known mistakes become executable refusals

Each validator should name the risk and point to the remediation path before payload generation continues.

MTR-TENANT-001

Write command missing explicit tenant

Block write-shaped commands that do not declare sandbox, production, or a single-tenant profile.

MTR-BILL-001

Billable workflow missing billing provider

Refuse invoice-producing workflows until billing provider state is known or explicitly planned.

MTR-BILL-002

Billing provider delivery method missing

Stripe attach preview requires exactly one supported delivery method path.

MTR-BILL-003

Existing config decision missing

Stripe attach preview requires fail-if-exists or reuse-if-matching and refuses archive or replace requests.

MTR-CREDIT-002

Invoice schedule uses non-fiat credit type

When `invoice_schedule.credit_type_id` is present, it must be fiat such as USD cents.

MTR-INV-003

Contract archive voids invoices without inventory

Archive paths that can void invoices require invoice and Stripe reconciliation context.

MTR-INV-004

Invoice issue-date edit lacks Stripe behavior

Issue-date preview refuses non-DRAFT invoices, wrong endpoint paths, missing contract-end proof, and unspecified Stripe behavior.

MTR-SUB-001

Subscription contract missing compatible wiring

Direct subscription previews require subscription product type, rate-card subscription-rate proof, collection schedule, proration, and read-back planning.

MTR-USAGE-001

Historical usage invoice-period risk not reviewed

Usage ingest previews require an explicit invoice period target, finalized-period review, preview-events proof, and read-back planning before canary or bulk ingest.

MTR-REPO-001

One-off script promoted into CLI workflow

Source-boundary validation rejects manifests that import old one-off or quarantined scripts as command handlers.

MTR-RATE-003

Product retirement skips rate closure

Product retirement preview refuses archive-only plans and requires rate-card close entries before archive.

MTR-RATE-005

Dimensional rate-card evidence incomplete

Dimensional previews require one action-code USAGE product, one compound billable-metric group key, reviewed rate rows, canary, and read-back planning.

Gotchas

Failure modes the CLI must prevent

  • Metronome sandbox and production share a base URL; the API key selects the tenant.
  • Some read endpoints are `POST`, while customers and invoice listing use path or query `GET` forms.
  • Package-based contract creation accepts a restricted payload; package extras need separate edit workflows.
  • Package plan moves use `updateEndDate` plus a `RENEWAL` successor; `SUPERSEDE` is not supported for package contracts.
  • Past-dated scheduled charges can finalize immediately and may push to Stripe quickly.
  • Product archive does not remove active rate-card entries; retirement requires `entitled: false` rate entries first.
  • Invoice issue-date edits are DRAFT-only, use `contracts/updateInvoiceIssueDate`, and need explicit Stripe behavior.
  • Customer create and search have distinct shapes: create uses `POST /v1/customers`, lookup/search use `GET`, ingest aliases are globally unique, and hierarchy belongs on contracts.
  • Subscription contract previews must prove product ID, billing frequency, and quantity or seat source before building `subscription_rate`.
  • Usage ingest needs stable transaction IDs, preview-events review, period targeting, and a canary read-back before bulk batches.
  • Generated artifacts are evidence-only, one-off scripts must stay out of command handlers, and Hyperline is historical unless legacy work is explicitly requested.
